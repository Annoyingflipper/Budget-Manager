# v2.2 Chunk 2 of 3 — App Shell

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the top header with a persistent sidebar on desktop and a bottom tab bar on mobile, and split the month controls out into their own dashboard-only toolbar.

**Architecture:** One `NAV_ITEMS` list feeds two presentations, so the sidebar and tab bar cannot drift apart. `AppShell` picks between them from `useIsMobile` and owns nothing else. `Toolbar` takes the month controls, which act on the dashboard's content rather than on which page is shown. `Header.tsx` retires.

**Tech Stack:** React 19, Vite 8, TypeScript 6, Tailwind 4 (CSS-first, no `tailwind.config.js`), Vitest 4 + React Testing Library 16, Playwright 1.60.

**Spec:** [`docs/superpowers/specs/2026-09-20-mesada-design-language-design.md`](../specs/2026-09-20-mesada-design-language-design.md)

## What the research changed about this chunk's risk

The spec predicted that `DashboardPage`, `SettingsPage`, `InsightsPage` and `AccountsPage` would all need rewriting. Reading them says otherwise:

- **Only `e2e/components/HeaderComponent.ts` is affected.** It is used by **8 spec files across 22 call sites**, but it is a page object — that is exactly the indirection it exists to provide. **Keep its public API identical and repoint its internals, and no spec file changes at all.** Treat any change to a `*.e2e.ts` file in this chunk as a signal you have taken a wrong turn.
- `SettingsPage`, `InsightsPage` and `AccountsPage` reference only their own page content plus a "Back to budget" button. They need nothing.

**The "Back to budget" buttons stay.** With a persistent nav they are redundant, but removing them is a polish decision that belongs with chunk 3's restyle, and keeping them means two more page objects and their specs stay untouched. Deleting them here would buy nothing and spend risk.

## Global Constraints

- **Test-first, no exceptions.** Write the test, run it, confirm it fails *for the intended reason*, then implement. Applies to rewritten tests too: run them red before changing the implementation.
- **`npm run typecheck` and `npm run build` are mandatory before every commit**, in addition to `npm test`. Vitest strips types through esbuild without checking them — a green suite is not evidence the build works. This hid a broken build for three consecutive tasks in v2.1.
- **Branch `staging`. Commit locally. Do not push.** `main` stays at v2.1 until all three chunks are smoked.
- **No new dependencies.**
- **Do not modify any file under `e2e/specs/`.** See above.
- **Do not stack `font-*` or `leading-*` utilities on a `text-*` step** — Tailwind resolves those through `var(--tw-font-weight, …)` / `var(--tw-leading, …)` and the stacked utility silently wins. Pick a different step instead.
- Use chunk 1's tokens: `text-display|title|heading|body|label|caption|money`, `rounded-control|card|chip`, `shadow-e1|e2|e3`. `docs/BRAND.md` is the reference.
- **`--radius-control` is 0.5rem but the app's existing row inputs use `rounded-md` (0.375rem).** That mismatch is chunk 3's decision. New shell components use `rounded-control`; do not migrate existing inputs here.
- **`npm test` is `vitest run --mode development`.** A bare `vitest run` fails: `.env.development.local` is not loaded and `src/lib/supabase.ts` throws at import.
- The bundle ceiling is **135 kB** gzipped (`npm run check:bundle`, currently 130.72). If the shell genuinely needs more, re-baseline it in the same commit with the reason in the message — do not delete the check.

### Task 2: The focus token

The spec requires visible focus on every interactive element. **The app currently has no focus-visible styling at all**, and chunk 1 deferred the token here deliberately, because a focus colour needs a designed value and this is where focus states get designed.

**Files:**
- Modify: `src/themes.css` (six blocks), `src/index.css` (`@theme` mapping + a base rule)
- Test: `src/theme/tokens.test.ts`

**Interfaces:**
- Produces: `--focus` per theme, mapped as `--color-focus`, plus a global `:focus-visible` outline. Tasks 3, 4 and 5 rely on focus being visible without doing anything per-component.

**Why a dedicated token rather than reusing `--text`.** `--text` and `--hero-bg` are the same value in every theme — the hero card inverts the palette — so a `--text` focus ring would be **invisible** on `GrandTotals`. Measured: contrast ratio exactly 1.00 in all six combinations. The values below clear 3:1 against `--bg`, `--card` **and** `--hero-bg`, staying in each theme's own hue.

- [ ] **Step 1: Write the failing test**

Append to `src/theme/tokens.test.ts`:

```ts
describe('focus ring', () => {
  // A focus ring can land on any surface in the app, so it owes WCAG's 3:1
  // non-text contrast against all three — including --hero-bg, which is why
  // --text cannot serve: --text IS --hero-bg in every theme (ratio 1.00), so a
  // --text ring would be invisible on the GrandTotals card.
  for (const theme of THEMES) {
    for (const mode of MODES) {
      it(`${theme}/${mode}: --focus clears 3:1 on --bg, --card and --hero-bg`, () => {
        const t = tokensFor(theme, mode);
        expect(t.focus, `${theme}/${mode} --focus is defined`).toMatch(/^#[0-9a-f]{6}$/);
        for (const surface of ['bg', 'card', 'hero-bg'] as const) {
          expect(contrastRatio(t.focus, t[surface]), `--focus on --${surface}`)
            .toBeGreaterThanOrEqual(3);
        }
      });
    }
  }

  it('is exposed to Tailwind and drives a global focus-visible outline', () => {
    const indexCss = readFileSync(resolve(__dirname, '../index.css'), 'utf8');
    expect(indexCss).toMatch(/--color-focus:\s*var\(--focus\)/);
    // The base rule is what makes focus visible everywhere without every
    // component remembering to style it.
    expect(indexCss).toMatch(/:focus-visible/);
  });
});
```

Create `src/components/SidebarNav.tsx`:

```tsx
import { useTheme } from '../theme/ThemeProvider';
import { supabase } from '../lib/supabase';
import { NAV_ITEMS, type Page } from '../navigation';
import Wordmark from './Wordmark';

type Props = {
  page: Page;
  onNavigate: (page: Page) => void;
};

/**
 * Desktop navigation. The mobile equivalent is TabBarNav; both render
 * NAV_ITEMS so they cannot drift apart.
 *
 * Icons are decorative and always paired with their label — the accessible
 * name is the label alone, so a screen reader never reads an emoji as the
 * destination.
 */
export default function SidebarNav({ page, onNavigate }: Props) {
  const { mode, setMode } = useTheme();

  return (
    <nav
      aria-label="Main"
      className="flex flex-col gap-1 w-56 shrink-0 p-4 bg-card rounded-card shadow-e1"
    >
      <div className="mb-4 px-2">
        <Wordmark />
      </div>

      {NAV_ITEMS.map((item) => (
        <button
          key={item.page}
          type="button"
          onClick={() => onNavigate(item.page)}
          aria-current={page === item.page ? 'page' : undefined}
          className={`flex items-center gap-2 text-label rounded-control px-3 py-2 text-left border-0 ${
            page === item.page ? 'bg-highlight text-text' : 'bg-transparent text-muted'
          }`}
        >
          <span aria-hidden="true">{item.icon}</span>
          {item.label}
        </button>
      ))}

      <div className="mt-auto pt-4 flex flex-col gap-1">
        <button
          type="button"
          onClick={() => setMode(mode === 'light' ? 'dark' : 'light')}
          aria-label="Toggle color mode"
          className="flex items-center gap-2 text-label rounded-control px-3 py-2 text-left border-0 bg-transparent text-muted"
        >
          <span aria-hidden="true">{mode === 'light' ? '🌙' : '☀️'}</span>
          {mode === 'light' ? 'Dark' : 'Light'}
        </button>
        <button
          type="button"
          onClick={() => { supabase.auth.signOut(); }}
          className="text-label rounded-control px-3 py-2 text-left border-0 bg-transparent text-muted"
        >
          Log out
        </button>
      </div>
    </nav>
  );
}
```

type Props = {
  selectedMonth: string;

  onNext,
