> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put every component on chunk 1's type, radius and elevation tokens, give every input a programmatic label, and make the dashboard axe scan pass unscoped.

## What the research changed about this chunk

I ran the unscoped axe scan before writing this plan, against the real QA backend with the E2E user's storage state, on four pages at two viewports. **Three of the four assumptions this chunk inherited were wrong.**

**1. The dashboard has exactly one violation rule, not two.** `CLAUDE.md` records the known debt as "the projected/actual inputs have no labels, and some text fails contrast." The contrast half is **already fixed** — chunk 1's token work cleared it. What remains:

```
===== DASHBOARD desktop : 1 rule(s) =====
  [critical] label (9 nodes)
      input[value="Internet"] / input[value="80"] / input[value="85"] …
```

All nine nodes are `LineItemRow`'s three inputs × three seeded rows. Identical at 375px. **`IncomeSummary` is not an offender** — despite the spec naming "the projected and actual money inputs" as the known problem, its inputs are wrapped in `<label>` elements and are correctly named. Do not "fix" them.

**2. Settings fails too, and its existing a11y test has been passing for the wrong reason.**

```
===== SETTINGS desktop : 1 rule(s) =====
  [critical] label (8 nodes)   ← every CategoryRow name input
```

`e2e/specs/theme-switching.e2e.ts` already runs an unscoped `wcag2a`/`wcag2aa` scan on Settings and asserts zero serious/critical violations. It passes because it waits only for the `Appearance` heading, which renders immediately, while `CategoriesEditor` fetches its categories asynchronously — **at scan time there are zero category rows on the page, so there is nothing for axe to fail on.** The test has been racing the data load since v1.5. Task 2 fixes the test as well as the markup; fixing only the markup would leave a green test that still proves nothing.

**3. `DraftRow`'s and `Accounts`' draft inputs never appear in a scan at all**, because both render only while a draft is open and no scan opens one. They are unlabelled in the same way. Fixed in Task 1 on the evidence of reading them, not of a scan.

**The page objects are safe.** `LineItemRowComponent` locates inputs by `type` within a `data-testid` root, and `CategoryRowComponent` by a `Delete <name>` button — neither reads an `aria-label`, so Task 1 needs no E2E changes. But **`CategoryRowComponent.root` is `page.locator('div.grid')`**, a structural locator: if Task 7 changes `CategoryRow`'s grid class, that page object breaks. It is the one locator in the suite that the restyle can reach.

## Global Constraints

- **Test-first, no exceptions.** Write the test, run it, confirm it fails *for the intended reason*, then implement. Applies to rewritten tests too.
- **`npm run typecheck` and `npm run build` are mandatory before every commit**, in addition to `npm test`. Vitest strips types through esbuild without checking them — a green suite is not evidence the build works.
- **Branch `staging`. Commit locally. Push only when the controller says so.** `main` stays at v2.1 until all three chunks are smoked.
- **No new dependencies.**
- **Do not stack `font-*` or `leading-*` utilities on a `text-*` step** — Tailwind 4 resolves both through `var(--tw-font-weight, …)` / `var(--tw-leading, …)` and the stacked utility silently wins over the step's own value. This chunk *removes* such stacks; it must never add one.
- **The sanctioned spacing subset is Tailwind's own scale limited to 0.5, 1, 1.5, 2, 2.5, 3, 4, 5, 6, 8, 12.** Binding on new work. This chunk is not a spacing migration — do not change padding or gaps except where a task says to.
- **`npm test` is `vitest run --mode development`.** A bare `vitest run` fails: `.env.development.local` is not loaded and `src/lib/supabase.ts` throws at import.
- The bundle ceiling is **135 kB** gzipped (`npm run check:bundle`, currently 130.03). A restyle should not move it; if it does, something is wrong — investigate rather than re-baselining.
- **Do not touch `src/components/MesadaMark.tsx`'s geometry.** `MesadaMark.test.tsx` asserts it stays in sync with `public/icon.svg` and asserts luminance ordering on `--neutral`/`--neutral-shade` and `--positive`/`--positive-shade` in all six theme × mode combinations. Both assertions were bought at real cost in v2.1.

## The two migration rules every restyle task follows

These are the whole substance of Tasks 5–9. Read them once; each task then names only its own files and its own exceptions.

### Rule A — type

Tailwind's default size utilities and all weight utilities are replaced by one of chunk 1's seven role steps. **Each step already carries its own weight and line-height**, so the `font-bold` / `font-extrabold` that currently sits beside a size utility is deleted, not translated.

| Replace | With | Because |
|---|---|---|
| `text-4xl` / `text-3xl` on a balance or total figure | `text-display` (2.5rem/800) | The largest thing on a screen. |
| `text-3xl` / `text-2xl` on a page `<h1>` | `text-title` (1.5rem/700) | Page and major section headings. |
| `text-xl` / `text-lg` on a card or section heading | `text-heading` (1.125rem/700) | Card headings, panel titles, category names. |
| `text-base` / `text-sm` on running prose or a description | `text-body` (0.9375rem/400) | Default running text. |
| `text-sm` / `text-xs` **with** `font-bold` or `font-extrabold`, on a form label, column header, or button | `text-label` (0.8125rem/600) | The mid weight the app never had. |
| `text-xs` on helper text, counts, hints, timestamps | `text-caption` (0.75rem/400) | Secondary information. |
| Any rendered money amount | `text-money` (0.9375rem/600, tabular) | Columns line up digit-for-digit. |

**Sizes that visibly change.** Expect these and check them in the screenshots; none is a mistake:

| from | to | change |
|---|---|---|
| `text-sm` 14px → `text-label` | 13px | slightly smaller, lighter (700→600) |
| `text-sm` 14px → `text-body` | 15px | slightly larger, much lighter (700→400 where bold was stacked) |
| `text-base` 16px → `text-body` | 15px | −1px |
| `text-xl` 20px → `text-heading` | 18px | −2px |
| `text-3xl` 30px → `text-title` | 24px | −6px |
| `text-4xl` 36px → `text-display` | 40px | +4px, and 700→800 |

**When a `font-*` utility sits on an element with no size utility**, it still goes: pick the step whose role matches and apply that instead. A bare `font-bold` on a `<span>` inside a caption-sized parent becomes `text-label` if it is a label, `text-money` if it is an amount.

**Colour utilities are untouched.** `text-muted`, `text-negative`, `text-positive`, `text-hero-text` and friends are colour tokens, not type steps, and they compose with a type step on the same element. Only the *size* and *weight* families move.

### Rule B — radius

The open question `docs/BRAND.md` left for this chunk is **resolved as: one control radius, and the row inputs adopt it.**

| Replace | With | Value change |
|---|---|---|
| `rounded-xl` (26 uses — cards, section containers) | `rounded-card` | none — 0.75rem both sides |
| `rounded-lg` (27 uses — auth screens, buttons) | `rounded-control` | none — 0.5rem both sides |
| `rounded-md` (33 uses — row and table inputs) | `rounded-control` | **0.375rem → 0.5rem, visible** |
| `rounded-sm` (4 uses) | `rounded-control` | 0.125rem → 0.5rem, visible |

**Why adopt rather than re-token.** `--radius-control` was chosen deliberately in chunk 1 as the designed value for buttons, inputs and date cells. The 0.375rem in the row inputs is not a competing design decision — it is what those components happened to be written with before any scale existed. Introducing a second control-radius token would encode that accident into the system permanently, and leaving the inputs un-tokenised would mean the densest, most-used surface in the app is the one place the manual does not describe. The cost is 2px of corner on ~33 inputs. **`docs/BRAND.md` §Radius and its "Known and open" entry are updated in Task 10 to record this as decided.**

**`rounded-full` stays.** Its only uses are `CategoryBudgetBar`'s two bar-fill elements. A progress bar is not a chip, and `--radius-chip` is documented as reserved for a pill component that does not exist yet. Mapping it would be a rename that makes the manual less true, not more.

### Rule C — elevation

| Replace | With |
|---|---|
| `shadow-xs` (2 uses) | `shadow-e1` |
| `shadow-lg` (1 use — `AttachmentViewer`'s dialog) | `shadow-e3` |

There is no `shadow-sm`/`shadow-md` in the codebase. Cards that currently carry **no** shadow do not gain one in this chunk — elevation is a separate visual decision and adding it everywhere at once would change the whole app's depth in a chunk whose other changes are already hard enough to smoke.

### Task 1: Give every input a programmatic label

The dashboard's only axe violation, plus the two draft inputs no scan ever reaches.

**Files:**
- Modify: `src/components/LineItemRow.tsx`, `src/components/DraftRow.tsx`, `src/components/CategoryRow.tsx`, `src/pages/Accounts.tsx`
- Test: `src/components/LineItemRow.test.tsx`, `src/components/DraftRow.test.tsx`, `src/components/CategoryRow.test.tsx`, `src/pages/Accounts.test.tsx`

**Interfaces:**
- Produces: the accessible names `Name for <item>`, `Projected for <item>`, `Actual for <item>` on `LineItemRow`; `Item name` on `DraftRow`; `Name for <category>` on `CategoryRow`; `New account name` on the `Accounts` draft. Task 2's axe scans depend on all of these existing.

**Naming convention, and one subtlety.** The app already uses `Balance for ${account.name}` and `Change icon for ${category.name}`, so row-scoped labels are the established pattern — and they matter here, because a screen-reader user tabbing a budget would otherwise hear "Projected" twenty times with no idea which row they are in.

**Label from the committed value, never the draft.** `LineItemRow` keeps the in-progress name in local state (`name`), separate from `item.name`. Build the label from **`item.name`** — a label rebuilt from `name` would change on every keystroke while the user is typing in the very field it labels, which screen readers announce.

```ts
import { test, expect } from '../fixtures/test';
import AxeBuilder from '@axe-core/playwright';

/**
 * The unscoped scans. Chunk 3's acceptance criterion is that these pass
 * without narrowing to a subtree.
 *
 * Every scan here waits for the page's ASYNC content before analysing.
 * That is not politeness — theme-switching.e2e.ts's Settings scan passed
 * for years while the page was failing, because it waited only for a
 * heading that renders immediately and scanned before CategoriesEditor's
 * fetch resolved. An axe scan that runs against an empty page is a green
 * test that proves nothing.
 */
async function seriousOrCritical(page: import('@playwright/test').Page) {
  const results = await new AxeBuilder({ page }).withTags(['wcag2a', 'wcag2aa']).analyze();
  return results.violations.filter((v) => v.impact === 'serious' || v.impact === 'critical');
}

test.describe('accessibility @a11y', () => {
  test('the dashboard has no serious or critical violations, unscoped', async ({
    dashboardPage,
  }) => {
    await dashboardPage.goto();
    // Wait for real line items, not just the shell: the nine unlabelled
    // inputs this scan exists to catch live inside CategoryTable's rows.
    await expect(dashboardPage.page.locator('input[type="number"]').first()).toBeVisible();

    const violations = await seriousOrCritical(dashboardPage.page);
    expect(violations, JSON.stringify(violations, null, 2)).toEqual([]);
  });

  test('the dashboard has no serious or critical violations on a phone', async ({
    dashboardPage,
  }) => {
    // The mobile layout is a different tree — tab bar instead of sidebar,
    // stacked rows instead of an 8-column grid.
    await dashboardPage.page.setViewportSize({ width: 375, height: 812 });
    await dashboardPage.goto();
    await expect(dashboardPage.page.locator('input[type="number"]').first()).toBeVisible();

    const violations = await seriousOrCritical(dashboardPage.page);
    expect(violations, JSON.stringify(violations, null, 2)).toEqual([]);
  });
});
```

### Task 3: The style ratchet

A source guard that bans the ad-hoc utilities, with an explicit allowlist of the files not yet migrated. Every later task deletes its own files from the allowlist, which is what makes "this surface is done" checkable instead of asserted.

**Files:**
- Create: `src/theme/styleRatchet.test.ts`

**Interfaces:**
- Produces: `UNMIGRATED`, an exported array of repo-relative paths. Tasks 4–9 each remove entries from it.

**Why a source scan is the right tool here, given this project's history.** Three defects in v2.1 and chunk 1 passed source-regex tests while the compiled output was wrong, and the lesson recorded in `CLAUDE.md` is to verify compiled output. That lesson does not apply to this guard and it is worth being clear why: this test asserts a property *of the source* — "no `.tsx` file writes an ad-hoc size utility" — not a property of what Tailwind emits. There is nothing downstream for the compiler to get wrong. The compiled-output risk in this chunk is the opposite one — that a token step does not render as specified — and that is already covered by `src/theme/tokens.test.ts` and the compiled-output section of `scripts/check-bundle-size.ts`.

/**
 * Tailwind's own size, weight, radius and shadow utilities — the ones
 * chunk 1's tokens replace. An optional variant prefix (sm:, hover:,
 * dark:) is allowed before the utility and still matches.
 *
 * Deliberately NOT matched: colour utilities (text-muted, text-negative),
 * alignment (text-right, text-center), and rounded-full, which stays —
 * CategoryBudgetBar's progress fills are not chips, and --radius-chip is
 * documented as reserved for a pill component that does not exist.
 */
const BANNED =
  /(?:^|[\s"'`{(])((?:[a-z-]+:)*)(text-(?:xs|sm|base|lg|xl|[2-9]xl)|font-(?:thin|extralight|light|normal|medium|semibold|bold|extrabold|black)|rounded-(?:none|sm|md|lg|xl|[2-9]xl)|shadow-(?:2xs|xs|sm|md|lg|xl|[2-9]xl))(?=[\s"'`})]|$)/g;

function tsxFiles(dir: string): string[] {
  return readdirSync(dir).flatMap((entry) => {
    const full = join(dir, entry);
    if (statSync(full).isDirectory()) return tsxFiles(full);
    if (!entry.endsWith('.tsx') || entry.endsWith('.test.tsx')) return [];
    return [full];
  });
}

function offendersIn(file: string): string[] {
  const text = readFileSync(file, 'utf8');
  return [...text.matchAll(BANNED)].map((m) => `${m[1]}${m[2]}`);
}

describe('style ratchet', () => {
  const files = tsxFiles(SRC).map((f) => relative(SRC, f)).sort();

  for (const file of files) {
    const allowed = UNMIGRATED.includes(file);
    it(`${file} ${allowed ? '(not yet migrated)' : 'uses only token utilities'}`, () => {
      const found = offendersIn(join(SRC, file));
      if (allowed) {
        // A file on the allowlist is EXPECTED to still have offenders. When it
        // has none, it has been migrated and must come off the list — otherwise
        // the ratchet silently stops guarding it.
        expect(found.length, `${file} is clean — delete it from UNMIGRATED`).toBeGreaterThan(0);
      } else {
        expect(found, `${file} uses ad-hoc utilities: ${found.join(', ')}`).toEqual([]);
      }
    });
  }

  it('the allowlist names only files that exist', () => {
    // A stale entry would silently excuse nothing while looking like debt.
    for (const file of UNMIGRATED) {
      expect(files, `${file} is on UNMIGRATED but is not a source file`).toContain(file);
    }
  });
});
